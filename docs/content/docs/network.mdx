Use network commands to intercept requests, mock responses, inspect traffic, and export HAR files during browser automation.

## Request routing

Routes apply before matching requests are sent. Set them before navigation when you need the first page load to be affected.

```bash
agent-browser open
agent-browser network route "**/analytics/**" --abort
agent-browser network route "**/api/users" --body '{"users":[]}'
agent-browser navigate https://app.example.com
```

<table>
  <thead>
    <tr><th>Command</th><th>Description</th></tr>
  </thead>
  <tbody>
    <tr><td><code>network route &lt;url&gt;</code></td><td>Intercept matching requests</td></tr>
    <tr><td><code>network route &lt;url&gt; --abort</code></td><td>Block matching requests</td></tr>
    <tr><td><code>network route &lt;url&gt; --body &lt;json&gt;</code></td><td>Fulfill matching requests with a mock body</td></tr>
    <tr><td><code>network route &lt;url&gt; --body &lt;json&gt; --allow-origin &lt;origin&gt;</code></td><td>Let a page on that origin read the mock cross-origin</td></tr>
    <tr><td><code>network route "*" --resource-type script --abort</code></td><td>Block only a specific resource type</td></tr>
    <tr><td><code>network unroute [url]</code></td><td>Remove one route or all routes</td></tr>
  </tbody>
</table>

`--resource-type` accepts comma-separated resource types such as `script`, `image`, `font`, `xhr`, and `fetch`.

A mock for a URL on another origin than the page (a page on `www.example.com` calling `api.example.com`) fails with a network error unless you pass `--allow-origin` with the page's origin. The mock then answers CORS checks and preflights for that origin only. JSON bodies are sent as `application/json`.

## Request log

```bash
agent-browser network requests
agent-browser network requests --filter api
agent-browser network requests --type xhr,fetch
agent-browser network requests --method POST
agent-browser network requests --status 2xx

agent-browser network requests --clear
```

## HAR export

```bash
agent-browser network har start

agent-browser open https://app.example.com
agent-browser click @e4

agent-browser network har stop ./trace.har
```

If HAR export fails, recording and captured requests remain available. Fix the destination and retry `network har stop`.

Text response bodies (JSON, HTML, JavaScript, form data) are embedded in the HAR as `content.text` by default, captured while the browser still has them buffered so they survive navigation. The `--content` flag on `har start` controls this:

<table>
  <thead>
    <tr><th>Mode</th><th>Behavior</th></tr>
  </thead>
  <tbody>
    <tr><td><code>--content text</code></td><td>Default. Embed text-like bodies (JSON, XML, HTML, JS, form data), up to 2&nbsp;MB per body.</td></tr>
    <tr><td><code>--content all</code></td><td>Embed every body; binary content is base64-encoded with <code>encoding: "base64"</code>.</td></tr>
    <tr><td><code>--content none</code></td><td>Sizes and MIME types only, no bodies.</td></tr>
  </tbody>
</table>

HAR files include request headers, response headers, cookies, POST data, and response bodies. Treat them as sensitive when pages use cookies, bearer tokens, or API keys.

## SSR and no-JavaScript debugging

```bash
agent-browser batch \
  "open" \
  "network route * --abort --resource-type script" \
  "navigate http://localhost:3000" \
  "snapshot -i"
```

Launching with `open` and no URL leaves the browser on `about:blank`, which gives routes time to register before the first real navigation.

## Saved flows

Saved flows are experimental. Open a session with `--capture flow`, do a browser task once, and agent-browser keeps the requests behind it. Later runs send those requests over HTTP and return only the data the task needs, without driving the page. Running a flow through the page or by replaying the recorded commands is not part of this feature yet.

```bash
agent-browser --capture flow open "https://shop.example.com/search?q=kettle"
agent-browser flow steps
agent-browser flow save search
agent-browser close

agent-browser flow run search --param q="toaster" --fields title,price --limit 3
```

### Capturing

`--capture flow` is a launch setting, like `--allowed-domains`. It records every command with the requests it caused until `close`. Passing it to a session that is already running without it relaunches the browser, as any changed launch setting does, and capture starts from that page. Later commands that repeat it or omit it do not relaunch. `flow` is the only supported value; any other value fails and lists the supported ones.

Every recorded command returns `recorded: {seq}` in its JSON response. Failed commands stay in the recording with `ok: false`, because a failed click may still have sent requests, but the saved file keeps only the requests. `close` reports `unsaved: {steps: N}` when steps after the last save exist.

`har start` and `har stop` are not available while capture owns the recorder. `har stop` fails with a message to use `flow save`.

Saving does not stop or reset the capture, so one session can save several flows. A flow can also start on a page that is already open, such as one where you are signed in.

`flow save` keeps:

- first-party JSON responses
- JSON that server-rendered pages embed in their HTML: `<script type="application/json">`, `__NEXT_DATA__`, JSON-LD and `window.x = {...}` state

It never saves cookies, `authorization`, or token and CSRF headers. Each run reads cookies from the live session.

The save report lists the requests it kept, the params, and any step it could not turn into a request, with the reason. When the recording stops at a sign-in form, the report says so.

Flow files are `version: 1`. A file with an unknown field, or any other version, fails to load with the reason.

### Params

Every value typed with `fill`, `type`, `keyboard type` or `inserttext` is either a param or redacted, and a step never stores it as a literal. A value typed into an ordinary field becomes a param named after the field, with `source: typed`; requests that carried it keep a `{{name}}` placeholder and the file keeps no copy of the value, so a run must pass `--param name=value`. A `--param` you give at save time names the value and keeps it as the recorded example. Values shorter than three characters are still params but are not replaced inside request URLs and bodies, to avoid rewriting unrelated text; secret fields are redacted whatever their length. Pass `flow save --param name=value` to choose the name. `flow save` also finds params on its own:

- a query value of the page URL that the requests also sent, such as `?q=` (`source: query`)
- a value the task picked from a list in an earlier response, such as an id from a list of stores (`source: response`)
- a value copied from a single field of an earlier response, such as a session key, which is filled from that response on every run

### Redaction

A value typed into a secret field is redacted in `flow steps`; the saved file never holds it. Keys sent with `press` or `keydown` while a secret field has focus are gathered into one secret and redacted the same way, and the password `auth login` fills from the vault is treated as a secret too. Only a bare key or Shift plus a key adds to that secret; a paste chord (`Control+v`, `Meta+v`, `Shift+Insert`) or `clipboard paste` into a secret field redacts the step, and the field's value is read once the paste finishes and treated as a secret in full, so a later request that sends it is not saved. When the page exposes no readable value (a contenteditable field, a cross-origin frame), the requests tagged to the paste step are dropped instead. The text of `clipboard write` is redacted and treated as a secret. Commands that are not recorded, such as `auth login`, tag no requests to a step. Any request that carried the value, as is or form-encoded, percent-encoded or JSON-escaped, is dropped from the flow, and the report names it by method and path (no query). When it was the only request, `flow save` fails with that name; fill a non-secret field or use a declared tool to make a reusable flow. agent-browser reads the field itself, or the focused element for `keyboard type` and `inserttext`, not only the command, so an unlabeled field is covered. A field is secret when:

### Running

```bash
agent-browser flow run <name> [--param k=v]... [--where field=value] [--fields a,b.c] [--limit n]
```

`--where` keeps items whose field contains the value, case-insensitively. `--fields` returns only those fields. Use them to keep large responses out of the agent's context. Unknown field names fail with the list of valid ones.

A run sends each request over direct HTTP, with cookies from the live session, in the order they were recorded; a later request can take a value from an earlier response.

Each request must stay on the flow's site, whatever `--allowed-domains` says. `flow save` records the base domain of the start URL, as defined by the public suffix list, so `a.vercel.app` does not allow `b.vercel.app`, and a run rejects any request or redirect to a host outside it. A flow whose origin directory does not match its start URL fails to load with a message to save it again.

A direct request is sent only to a public address, checked when its host resolves and again on every redirect, so a name that later resolves to a loopback, private or link-local address (for example `169.254.169.254`) is refused with a clear error and nothing is sent. A flow recorded against `localhost`, `*.localhost` or a local IP address runs only against local addresses; other hostnames that resolve to local addresses, such as a `.test` dev domain, are refused. A proxy from `HTTP_PROXY`, `HTTPS_PROXY` or `ALL_PROXY` is used as configured, at any address; requests that go through it are resolved and checked by the proxy, not by agent-browser. A target that `NO_PROXY` excludes connects directly and is checked like any other. A proxy name that is an `https://` hostname is trusted by the resolver, so a direct target with that same name skips the filter. The address of an `http://` proxy named by a hostname is looked up once when the run starts; if that fails the run stops with `could not resolve proxy <host>`.

Every response is checked against the shape that was recorded. If the shape changed, the run fails with `drifted`, the flow is marked unverified, and the agent continues in the page and saves the flow again. The message names the recorded key that is missing and, when a list appeared elsewhere, where. The path of the main list is saved with each request, so a list nested deeper than the shape is checked too. A recorded list that is missing from the response, or no longer a list, is drift, even when the answer looks empty, because a missed drift returns a silently wrong empty answer. A list that is present and empty is an empty result, and a response that only lacks the counts of an empty list leaves the verified state as it was.

Some responses end the run. Except `drifted`, they do not mark the flow unverified, and the run adds no throttle or retry of its own.

A bot challenge is recognized only in HTML responses, never in JSON. A write is sent once: if the request fails without an answer, the result is `outcome_unknown`, because the server may have applied it, and it is never retried. A write never follows a redirect, including a 307 or 308: the 3xx is its answer and the run stops with it. A read follows redirects only within the flow's site. The code is in the JSON response as `code`, with `data.status`, `data.step` and `data.httpStatus`.

### Writes

`flow save` lists every write among the saved requests in the flow's `writes`, each with an id, a method, a URL and a kind. The report prints them.

<table>
  <thead>
    <tr><th>Kind</th><th>What it is</th></tr>
  </thead>
  <tbody>
    <tr><td><code>explicit</code></td><td>Any request other than GET, HEAD or OPTIONS, except GraphQL queries</td></tr>
    <tr><td><code>suspected</code></td><td>A GET whose path has a whole segment of <code>logout</code>, <code>signout</code>, <code>unsubscribe</code>, <code>delete</code> or <code>remove</code>. <code>/address</code> does not match</td></tr>
  </tbody>
</table>

```bash
agent-browser flow run <name> --allow-write <all|id,id,...>
```

`--allow-write` takes `all` or comma-separated write ids. A run only sends the writes among the requests its output needs, and a write `--allow-write` does not cover is never sent silently: the run stops with a confirmation request, and `confirm` approves one write at a time. Each write is a policy action named `flow_write:<id>`, so `--action-policy` can deny or require confirmation for it and `--confirm-actions flow_write:<id>` asks even when `--allow-write` covers it. 

A body is read as a form when its content type says so or when it has the shape `k=v&k=v`, whatever its content type. A value that could break the structure of a header, a plain text body or a multipart body, such as a line break or the multipart boundary, is refused before anything is sent. A value is encoded for where it lands: a URL query or path segment, a form body, or a JSON string. Placeholders are filled in one pass, so a value that contains placeholder text is inserted as data. A flow with no `output` sends every request, and every write among them is gated like any other. A param never fills the text of a GraphQL operation; it fills `variables` and the other fields. An operation with a placeholder in its text counts as a write, and a run refuses, before sending anything, a request that becomes a write once its values are filled in but is not in `writes`.

### Discovery

After `open`, `back`, `forward`, `reload` or a tab switch, the response lists the saved flows for that site once per session, with their params, the recorded values and the item fields. A capturing session hides only the flows it saved itself. When the page also declares WebMCP tools, those come first and the hint suggests them when one covers the task.

Saved flows use the shape of a WebMCP tool: a name, a description and an `inputSchema` built from the params. `flow list --json` returns that shape, and `webmcp list` shows saved flows in it, after the tools the page declares. Run them with `flow run`; `webmcp invoke` only calls the page's own tools.

The MCP server exposes `agent_browser_flow_list`, `agent_browser_flow_run`, `agent_browser_flow_steps` and `agent_browser_flow_save` in the core profile. The common `capture` argument opens a session with `--capture flow`.

### Storage

Flows live in `~/.agent-browser/flows/<origin>/<name>.json`. Set `AGENT_BROWSER_FLOWS_DIR` to use another directory. `<origin>` is validated as a hostname when a flow is written, so it cannot contain a path.

On macOS and Linux the directories are created with mode `0700` and the files with `0600`. On Windows flows are written under the user profile and inherit its per-user permissions; agent-browser does not set an explicit ACL, so a directory set with `AGENT_BROWSER_FLOWS_DIR` is only as private as its location.
