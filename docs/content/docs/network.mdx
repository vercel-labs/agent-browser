Use network commands to intercept requests, mock responses, inspect traffic, and export HAR files during browser automation.

## Request routing

Routes apply before matching requests are sent. Set them before navigation when you need the first page load to be affected.

```bash
agent-browser open
agent-browser network route "**/analytics/**" --abort
agent-browser network route "**/api/users" --body '{"users":[]}'
agent-browser navigate https://app.example.com
```

<table>
  <thead>
    <tr><th>Command</th><th>Description</th></tr>
  </thead>
  <tbody>
    <tr><td><code>network route &lt;url&gt;</code></td><td>Intercept matching requests</td></tr>
    <tr><td><code>network route &lt;url&gt; --abort</code></td><td>Block matching requests</td></tr>
    <tr><td><code>network route &lt;url&gt; --body &lt;json&gt;</code></td><td>Fulfill matching requests with a mock body</td></tr>
    <tr><td><code>network route &lt;url&gt; --body &lt;json&gt; --allow-origin &lt;origin&gt;</code></td><td>Let a page on that origin read the mock cross-origin</td></tr>
    <tr><td><code>network route "*" --resource-type script --abort</code></td><td>Block only a specific resource type</td></tr>
    <tr><td><code>network unroute [url]</code></td><td>Remove one route or all routes</td></tr>
  </tbody>
</table>

`--resource-type` accepts comma-separated resource types such as `script`, `image`, `font`, `xhr`, and `fetch`.

A mock for a URL on another origin than the page (a page on `www.example.com` calling `api.example.com`) fails with a network error unless you pass `--allow-origin` with the page's origin. The mock then answers CORS checks and preflights for that origin only. JSON bodies are sent as `application/json`.

## Request log

```bash
agent-browser network requests
agent-browser network requests --filter api
agent-browser network requests --type xhr,fetch
agent-browser network requests --method POST
agent-browser network requests --status 2xx
agent-browser network request <requestId>
agent-browser network requests --clear
```

<table>
  <thead>
    <tr><th>Filter</th><th>Description</th></tr>

Use `network request <requestId>` to inspect one request and response in detail after finding its ID in `network requests`.

## HAR export

```bash
agent-browser network har start

agent-browser open https://app.example.com
agent-browser click @e4

agent-browser network har stop ./trace.har
```

If HAR export fails, recording and captured requests remain available. Fix the destination and retry `network har stop`.

Text response bodies (JSON, HTML, JavaScript, form data) are embedded in the HAR as `content.text` by default, captured while the browser still has them buffered so they survive navigation. The `--content` flag on `har start` controls this:

<table>
  <thead>
    <tr><th>Mode</th><th>Behavior</th></tr>
  </thead>
  <tbody>
    <tr><td><code>--content text</code></td><td>Default. Embed text-like bodies (JSON, XML, HTML, JS, form data), up to 2&nbsp;MB per body.</td></tr>
    <tr><td><code>--content all</code></td><td>Embed every body; binary content is base64-encoded with <code>encoding: "base64"</code>.</td></tr>
    <tr><td><code>--content none</code></td><td>Sizes and MIME types only, no bodies.</td></tr>
  </tbody>
</table>

HAR files include request headers, response headers, cookies, POST data, and response bodies. Treat them as sensitive when pages use cookies, bearer tokens, or API keys.

## SSR and no-JavaScript debugging

```bash
agent-browser batch \
  "open" \
  "network route * --abort --resource-type script" \
  "navigate http://localhost:3000" \
  "snapshot -i"
```

Launching with `open` and no URL leaves the browser on `about:blank`, which gives routes time to register before the first real navigation.

## Saved flows

Saved flows are experimental. Open a session with `--capture flow`, do a browser task once, and agent-browser keeps the requests behind it. Later runs replay those requests and return only the data the task needs, without driving the page.

```bash
agent-browser --capture flow open "https://shop.example.com/search?q=kettle"
agent-browser flow steps
agent-browser flow save search
agent-browser close

agent-browser flow run search --param q="toaster" --fields title,price --limit 3
```

### Capturing

`--capture flow` is a launch option, like `--allowed-domains`. It applies when the session opens and records every command with the requests it caused until `close`. Passing it to a session that is already running without it fails with a message to close and reopen. `flow` is the only supported value; any other value fails and lists the supported ones.

Every recorded command returns `recorded: {seq}` in its JSON response. Failed commands stay in the recording with `ok: false`, because a failed click may still have sent requests. `close` reports `unsaved: {steps: N}` when steps after the last save exist.

`har start` and `har stop` are not available while capture owns the recorder. `har stop` fails with a message to use `flow save`.

### Steps and saving

`flow steps` lists the recorded steps.

  <thead>
    <tr><th>Column</th><th>Meaning</th></tr>

    <tr><td><code>seq</code></td><td>Step number, the same one returned as <code>recorded.seq</code></td></tr>
    <tr><td><code>command</code></td><td>The command and its main argument</td></tr>
    <tr><td><code>url</code></td><td>The page URL after the command</td></tr>
    <tr><td><code>requests</code></td><td>Requests the command caused</td></tr>
    <tr><td><code>ok</code></td><td>Whether the command succeeded</td></tr>
  </tbody>

`flow steps --json` returns the same data.

```bash
agent-browser flow save <name> [--from <seq|open|last-save>] [--to <seq>] [--param k=v]... [--output <id>] [--description <text>]
```

<table>
  <thead>
    <tr><th>Option</th><th>Meaning</th></tr>
  </thead>
  <tbody>
    <tr><td><code>--from</code></td><td>First step. A step number, <code>open</code> for the last navigation, or <code>last-save</code> for the step after the previous save. Defaults to the last navigation after the previous save</td></tr>
    <tr><td><code>--to</code></td><td>Last step. Defaults to the latest</td></tr>
    <tr><td><code>--param</code></td><td>A value you typed during the task, so later runs can change it</td></tr>
    <tr><td><code>--output</code></td><td>Request id whose response the flow returns</td></tr>
    <tr><td><code>--description</code></td><td>One line saying what the flow does, shown in flow lists</td></tr>
  </tbody>
</table>

Saving does not stop or reset the capture, so one session can save several flows. A flow can also start on a page that is already open, such as one where you are signed in.

`flow save` keeps:

- first-party JSON responses
- JSON that server-rendered pages embed in their HTML: `<script type="application/json">`, `__NEXT_DATA__`, JSON-LD and `window.x = {...}` state

It never saves cookies, `authorization`, or token and CSRF headers. Each run reads cookies from the live session.

The save report lists the requests it kept, the params, and any step it could not turn into a request, with the reason. When the recording stops at a sign-in form, the report says so.

Flow files are version 2. A flow saved by an earlier version fails to run with a message to save it again.

### Params

Every value typed with `fill` or `type` is either a param or redacted, and a step never stores it as a literal. A value typed into an ordinary field becomes a param named after the field, with `source: typed`; the step keeps a `{{name}}` placeholder and the value survives only as the param's recorded example. Pass `flow save --param name=value` to choose the name. `flow save` also finds params on its own:

- a query value of the page URL that the requests also sent, such as `?q=` (`source: query`)
- a value the task picked from a list in an earlier response, such as an id from a list of stores (`source: response`)
- a value copied from a single field of an earlier response, such as a session key, which is filled from that response on every run

### Redaction

A value typed into a secret field is stored as `<redacted>` and listed in `redactedSteps`. Any request that carried the value is dropped from the flow, and the flow cannot be replayed through the UI. agent-browser reads the field itself, not only the command, so an unlabeled field is covered. A field is secret when:

<table>
  <thead>
    <tr><th>Signal</th><th>Matches</th></tr>
  </thead>
  <tbody>
    <tr><td><code>type</code></td><td><code>password</code></td></tr>
    <tr><td><code>autocomplete</code></td><td><code>current-password</code>, <code>new-password</code>, <code>one-time-code</code>, or any <code>cc-*</code> token</td></tr>
    <tr><td>Name, id, label, placeholder, aria-label or selector</td><td>Contains <code>pass</code>, <code>secret</code>, <code>token</code>, <code>otp</code>, <code>pin</code>, <code>cvv</code> or <code>card</code></td></tr>
  </tbody>
</table>

```bash
agent-browser flow list   # Params, recorded values, item fields and verified state
```

### Running

```bash
agent-browser flow run <name> [--param k=v]... [--where field=value] [--fields a,b.c] [--limit n]
```

`--where` keeps items whose field contains the value, case-insensitively. `--fields` returns only those fields. Use them to keep large responses out of the agent's context. Unknown field names fail with the list of valid ones.

A run tries, in order:

1. direct HTTP, with cookies from the live session
2. the same request sent from the page, which adds the browser's own headers
3. a replay of the recorded commands, which reads the request the page sends

Each request must stay on the flow's site, whatever `--allowed-domains` says. `flow save` records the base domain of the start URL as `allowedHosts`, and a run rejects any request, redirect or navigation to a host outside it, so an edited flow file cannot send the session's cookies elsewhere. `--allowed-domains` still applies on top. The in-page tier runs only when the active tab is already on the flow's site; otherwise it is skipped, with the reason in the run's `fellBack` list, and the run continues with the next tier.

The next run starts at the tier that worked. Every tier checks the response against the shape that was recorded. If the shape changed, the run fails, the flow is marked unverified, and the agent continues in the UI. A response that only lacks its lists and counts is treated as no results and leaves the verified state as it was.

### Writes

`flow save` lists every write the recorded steps caused in the flow's `writes`, each with an id, a method, a URL and a kind. The report prints them.

<table>
  <thead>
    <tr><th>Kind</th><th>What it is</th></tr>
  </thead>
  <tbody>
    <tr><td><code>explicit</code></td><td>Any request other than GET, HEAD or OPTIONS, except GraphQL queries</td></tr>
    <tr><td><code>suspected</code></td><td>A GET that looks like a state change: a data request fired by a click that no output depends on, or a path with a whole segment of <code>logout</code>, <code>signout</code>, <code>unsubscribe</code>, <code>delete</code> or <code>remove</code>. <code>/address</code> does not match</td></tr>
  </tbody>
</table>

```bash
agent-browser flow run <name> --allow-write <all|id,id,...>
```

`--allow-write` takes `all` or comma-separated write ids. A write it does not cover is never sent silently: the run stops with a confirmation request, and `confirm` approves one write at a time. Each write is a policy action named `flow_write:<id>`, so `--action-policy` can deny or require confirmation for it and `--confirm-actions flow_write:<id>` asks even when `--allow-write` covers it. These checks apply to the HTTP and in-page tiers. The command replay also sends writes no kept request covers; those need `--allow-write` or a confirmation too, and the policy file can deny them. A write the site accepted is never sent again by a lower tier.

### Discovery

After `open`, `back`, `forward`, `reload` or a tab switch, the response lists the saved flows for that site once per session, with their params, the recorded values and the item fields. A capturing session hides only the flows it saved itself. When the page also declares WebMCP tools, those come first and the hint suggests them when one covers the task.

Saved flows use the shape of a WebMCP tool: a name, a description and an `inputSchema` built from the params. `flow list --json` returns that shape, and `webmcp list` shows saved flows in it, after the tools the page declares. Run them with `flow run`; `webmcp invoke` only calls the page's own tools.

The MCP server exposes `agent_browser_flow_list`, `agent_browser_flow_run`, `agent_browser_flow_steps` and `agent_browser_flow_save` in the core profile. The common `capture` argument opens a session with `--capture flow`.

### Storage

Flows live in `~/.agent-browser/flows/<origin>/<name>.json`. Set `AGENT_BROWSER_FLOWS_DIR` to use another directory. `<origin>` is validated as a hostname when a flow is written, so it cannot contain a path.

On macOS and Linux the directories are created with mode `0700` and the files with `0600`. On Windows flows are written under the user profile and inherit its per-user permissions; agent-browser does not set an explicit ACL, so a directory set with `AGENT_BROWSER_FLOWS_DIR` is only as private as its location.
