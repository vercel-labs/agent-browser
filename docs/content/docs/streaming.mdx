Stream the browser viewport via WebSocket for live preview or "pair browsing" where a human can watch and interact alongside an AI agent.

## Event subscriptions

A subscription watches for something in the page and stores what happens on the session's event bus, so an agent or script can act, end its turn, and learn about the result without polling. The bus runs inside the daemon and adds no port or listener. Every operation goes through the same action policy and output limits as the rest of the CLI.

Chrome is the only supported engine. Other engines return an unsupported error.

Start the subscription before the action that triggers the change:

```bash
agent-browser events start --selector '#deploy-complete'
agent-browser click '#deploy'
agent-browser events wait ev_1a2b3c4d
```

The CLI, MCP tools and eve tools expose start, read, ack, list and stop with the same JSON results. `wait` and `watch` are CLI conveniences over read. Ctrl-C stops a `watch` loop and leaves the subscription in place, so `events stop <id>` or the TTL ends it.

### Start a subscription

```bash
agent-browser events start --selector <css> [--state visible|hidden] [--once] [--ttl <secs>] [--owner <label>] [--key <key>]
```

<table>
  <thead>
    <tr><th>Flag</th><th>Meaning</th></tr>
  </thead>
  <tbody>
    <tr><td><code>--selector</code></td><td>CSS selector to observe in the current document.</td></tr>
    <tr><td><code>--state</code></td><td><code>visible</code> (default) or <code>hidden</code>. Selector sources emit <code>element.visible</code> and <code>element.hidden</code>; this picks which transition is stored.</td></tr>
    <tr><td><code>--once</code></td><td>Ends the subscription after its first stored event with reason <code>matched</code>.</td></tr>
    <tr><td><code>--ttl</code></td><td>Lifetime in seconds. Defaults to 600 and is capped at 1800.</td></tr>
    <tr><td><code>--owner</code></td><td>Label stored with the subscription. <code>ack</code> and <code>stop</code> with an owner only touch subscriptions carrying that owner.</td></tr>
    <tr><td><code>--key</code></td><td>Idempotency key. Starting again with the same key and rule returns the existing subscription id.</td></tr>
  </tbody>
</table>

The start result contains `id`, `head`, `alreadySatisfied`, `expiresAt`, `owner` and the tab's display id, label and target id. `alreadySatisfied` is true when the requested state already holds at arm time. That initial state is reported in `subscription.ready` and does not create an event; events are stored on later transitions.

At most 20 subscriptions are active at once. Finished subscriptions stay readable for 10 minutes, and `events list` shows at most 50 entries.

A subscription is bound to the current tab. Closing or crashing that tab ends it with `tab_closed` or `tab_crashed`. Page observers re-arm after navigation, so a subscription survives a new document. Same-document and new-document navigation each produce a `subscription.rearmed` marker. If the condition already holds in the new document, the initial observation is stored as an event flagged `afterNavigation`, so a click that navigates and then shows the expected element still matches.

### Read, cursors and acks

```bash
agent-browser events read <id> [--since <cursor>] [--wait <ms>] [--limit <n>] [--ack]
```

A read returns `status`, `events`, `cursor`, `head`, `consumed` and `waiting`. `cursor` is the cursor after the last returned item, which is the value to pass as the next `--since`. The client holds its own cursor; the daemon stores only the `consumed` watermark.

A cursor is opaque and shaped like `<subscription id>:<seq>`, for example `ev_1a2b3c4d:4`. An omitted `--since` starts at the oldest retained item. A cursor from another subscription or from ahead of the head returns `cursor_invalid`. An id the daemon no longer knows, including after a daemon restart or idle shutdown, returns an explicit daemon-restarted error.

`--limit` caps the number of returned items. `--wait` bounds how long the read blocks. `waiting` is true when the wait timed out with nothing new.

A plain read never moves `consumed`. `--ack` advances it to the last sequence number returned, and only when that is above the current value. `events wait` is a read with `--wait` and `--ack`. Replays and limit-truncated reads therefore never move the watermark backwards or past an event that was not returned. MCP and chat tools clamp their waits instead of raising their own time limits.

### List and unread events

```bash
agent-browser events list [--owner <label>] [--unread]
```

Each entry has `id`, `status`, `reason`, `rule`, `owner`, `head`, `consumed`, `dropped`, `tab` and `expiresAt`. `status` is `waiting` while the subscription is armed, then `matched`, `timeout`, `cancelled` or `ended`; `reason` carries the specific end reason. `dropped` counts events removed by the buffer bounds.

`--unread` returns only subscriptions whose `head` is above `consumed`, so a hook or script can test for pending events with one command and no JSON parsing. An empty list means nothing is waiting.

Finished subscriptions end with a reason: `matched` for `--once`, `timeout` for TTL expiry, `cancelled` for `events stop`, `tab_closed`, `tab_crashed`, `browser_closed`, or `policy_denied` when a policy check or reload stops the subscription.

### Envelopes and markers

Every stored item is a versioned envelope. `meta` is generated by the bus and safe to put in model-visible text. `data` comes from the page, is capped, and is untrusted.

```json
{
  "version": "agent-browser.event.v1",
  "meta": {
    "eventId": "9d0f6a8e-1f5d-4b4e-9a8a-3f7a1c2d4e5f",
    "name": "element.visible",
    "timestamp": "2026-10-21T18:12:44.120Z",
    "cursor": "ev_1a2b3c4d:4",
    "subscriptionId": "ev_1a2b3c4d",
    "session": "default",
    "tab": { "id": "t1", "label": "Deploy", "targetId": "8A2C..." }
  },
  "data": { "state": "visible", "label": "Deploy complete", "afterNavigation": false }
}
```

<table>
  <thead>
    <tr><th>Marker</th><th>Meaning</th></tr>
  </thead>
  <tbody>
    <tr><td><code>subscription.ready</code></td><td>Initial observation for the subscription or for a new document. A late joiner sharing an observer gets the current state here.</td></tr>
    <tr><td><code>subscription.rearmed</code></td><td>The page observer re-armed after a same-document or new-document navigation. The subscription continues.</td></tr>
    <tr><td><code>subscription.gap</code></td><td>Events were lost to buffer bounds or CDP lag. <code>data.missed</code> carries the count. The subscription continues, and a page observer next stores a current-state observation flagged <code>afterGap</code>.</td></tr>
    <tr><td><code>subscription.ended</code></td><td>The subscription ended. <code>data.reason</code> names why.</td></tr>
  </tbody>
</table>

A `gap` means a transition that came and went entirely inside the loss cannot be reported; the `afterGap` observation tells you whether the condition holds now. Neither a gap nor a slow reader ends a subscription.

### Selector recipes

An element appears:

```bash
agent-browser events start --selector '#deploy-complete' --once
agent-browser click '#deploy'
agent-browser events wait ev_1a2b3c4d
```

An element disappears:

```bash
agent-browser events start --selector '#progress' --state hidden --once
agent-browser click '#cancel'
agent-browser events wait ev_1a2b3c4d
```

Wait after a click that navigates:

```bash
agent-browser events start --selector '[role="dialog"]' --once
agent-browser click '#open-settings'
agent-browser events wait ev_1a2b3c4d
```

The re-arm and `afterNavigation` behavior covers a click that reloads the document before the dialog appears.

## Harness setup

The bus does not know about any particular harness. These recipes use only the public verbs, return only bus metadata, and tell the agent to run `events read` for the event itself. Never paste page strings from a wake message into a prompt.

### Claude Code

A `Stop` hook that blocks the end of a turn while unread events exist. Write `.claude/hooks/events-unread.sh`:

```bash
#!/bin/bash
set -euo pipefail
pending=$(agent-browser events list --unread --json)
if [ "$(jq '.data.subscriptions | length' <<<"$pending")" -eq 0 ]; then
  exit 0
fi
ids=$(jq -r '[.data.subscriptions[].id] | join(", ")' <<<"$pending")
jq -n --arg ids "$ids" '{
  decision: "block",
  reason: "Browser events are waiting for subscription(s): " + $ids + ". Run agent-browser events read <id> --ack to see them."
}'
```

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/events-unread.sh"
          }
        ]
      }
    ]
  }
}
```

The agent reads and acknowledges the event on the next turn, so the hook stops blocking. Claude Code limits consecutive Stop continuations, and the documented `stop_hook_active` input is available if the script needs to check it.

An `async` hook with `asyncRewake` waits in the background and wakes the agent on exit code 2. Write `.claude/hooks/await-event.sh`:

```bash
#!/bin/bash
id=$(agent-browser events list --unread --json | jq -r '.data.subscriptions[0].id // empty')
[ -n "$id" ] || exit 0
result=$(agent-browser events wait "$id" --timeout 60000 --json)
[ "$(jq '.data.events | length' <<<"$result")" -gt 0 ] || exit 0
echo "A browser event is ready. Run agent-browser events read $id to see it." >&2
exit 2
```

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/await-event.sh",
            "async": true,
            "asyncRewake": true
          }
        ]
      }
    ]
  }
}
```

A plain background wait is enough when the harness can run a shell task and wake the agent from its output:

```bash
agent-browser events wait ev_1a2b3c4d --timeout 120000
```

### Cursor

A `stop` hook that returns a `followup_message` while unread events exist. Write `.cursor/hooks/events-unread.sh`:

```bash
#!/bin/bash
cat > /dev/null
pending=$(agent-browser events list --unread --json)
if [ "$(jq '.data.subscriptions | length' <<<"$pending")" -eq 0 ]; then
  echo '{}'
  exit 0
fi
ids=$(jq -r '[.data.subscriptions[].id] | join(", ")' <<<"$pending")
jq -n --arg ids "$ids" '{
  followup_message: ("Browser events are waiting for subscription(s): " + $ids + ". Run agent-browser events read <id> --ack to see them.")
}'
```

```json
{
  "version": 1,
  "hooks": {
    "stop": [{ "command": ".cursor/hooks/events-unread.sh" }]
  }
}
```

Cursor applies its own loop limit to repeated follow-ups.

### Shell or script loop

`events watch` writes one envelope per line and is safe to pipe into `jq` or another program:

```bash
id=$(agent-browser events start --selector '#deploy-complete' --json | jq -r '.data.id')
agent-browser click '#deploy'
agent-browser events watch "$id" | jq -c '.meta | {name, cursor, subscriptionId}'
```

The loop prints only bus metadata. Run `agent-browser events read "$id" --ack` to collect the envelopes, or use `events ack` after processing them.

## Streaming

Every session automatically starts a WebSocket stream server on an OS-assigned port. The server streams viewport frames and accepts input events (mouse, keyboard, touch).

To bind to a specific port, set `AGENT_BROWSER_STREAM_PORT`:

```bash
AGENT_BROWSER_STREAM_PORT=9223 agent-browser open example.com
```

You can also manage streaming at runtime:

```bash
agent-browser stream status            # Show streaming state and bound port
agent-browser stream enable --port 9223  # Re-enable on a specific port
agent-browser stream disable           # Stop streaming for the session
```

`stream status` returns the enabled state, active port, browser connection state, and whether screencasting is active. `stream disable` tears the server down and removes the session's `.stream` metadata file.

Use [Video Recording](/recording) when you need a saved WebM or MP4 artifact instead of a live WebSocket stream. Recording requires `ffmpeg` on `PATH`.

## Runtime status response

`agent-browser stream status --json` returns data like:

```json
{
  "enabled": true,
  "port": 9223,
  "connected": true,
  "screencasting": true
}
```

`connected` reports whether the daemon currently has a browser attached. `screencasting` reports whether frames are actively being produced for the stream server.

## Relationship to screencast commands

`stream enable` creates the WebSocket server and keeps it available for the session. WebSocket clients then trigger live frame delivery automatically.

The lower-level `screencast_start` and `screencast_stop` commands still control explicit CDP screencasts directly. Use them when you want a screencast without the WebSocket runtime server.

## WebSocket protocol

Connect to `ws://localhost:9223` to receive frames and send input.

Frame encoding is set per daemon with `AGENT_BROWSER_STREAM_QUALITY` (0 to 100), `AGENT_BROWSER_STREAM_MAX_WIDTH` and `AGENT_BROWSER_STREAM_MAX_HEIGHT`. The live stream requests jpeg. An explicit `screencast_start` reconfigures the same underlying screencast, so a client can see the format change mid-stream. Width and height cap the frame and default to the session viewport. On a busy page at 1280x720, quality 80 costs about 54 KB per frame, quality 20 about 25 KB, and quality 20 at 640x360 about 9 KB.

Browser clients must load from `localhost`, `127.0.0.1`, `::1` or `file://`. Any other origin gets a 403 on the upgrade and needs a proxy.

### Frame messages

The server sends frame messages with base64-encoded images:

```json
{
  "type": "frame",
  "seq": 41,
  "data": "<base64-encoded-jpeg>",
  "metadata": {
    "deviceWidth": 1280,
    "deviceHeight": 720,
    "pageScaleFactor": 1,
    "offsetTop": 0,
    "scrollOffsetX": 0,
    "scrollOffsetY": 0,
    "timestamp": 1785038682238
  }
}
```

`seq` is a monotonic frame id. It is what an ack pacing client echoes back, and it keeps climbing across browser relaunches so a long-lived client never sees an id go backwards.

`metadata.timestamp` is the capture time in epoch milliseconds. Comparing it against the clock when the frame is drawn gives the age of what is on screen, which is the number worth watching on a constrained link.

### URL messages

On Chrome, the server sends URL updates for full-document, History API, and fragment navigation in the active tab's main frame:

```json
{
  "type": "url",
  "url": "https://example.com/dashboard#activity",
  "timestamp": 1785038682238
}
```

Navigation inside child frames or background tabs does not emit a URL message or replace the active tab's cached URL.

### Status messages

Connection and screencast status:

```json
{
  "type": "status",
  "connected": true,
  "screencasting": true,
  "viewportWidth": 1280,
  "viewportHeight": 720
}
```

### Frame delivery

Frames are delivered latest-first: the server holds only the newest frame and reads it at send time, so every frame produced while an earlier one is still being written is skipped instead of queued. The application never builds a backlog.

In the default push pacing the transport underneath still can: frames already accepted by the socket are delivered in order, so a client that stops reading entirely drains whatever the kernel buffered before the writer blocked. Ack pacing removes that window (see below). Status, console, and tab messages flow through a separate ordered channel, so they are never replaced by a newer message the way frames are. They are not unconditionally durable: a client that falls far enough behind can lag out of that channel and lose messages, so treat console output as a live feed rather than an audit log.

Input handling is independent of frame delivery. Each connection reads input on its own task, so clicks and keystrokes dispatch to the browser immediately even while a large frame is mid-write to a slow client. Events go to the browser without waiting for its reply, so a click stays responsive behind a burst of mouse moves, and ordering is preserved.

### Client configuration

A client can cap its own frame rate by sending a `config` message at any time:

```json
{
  "type": "config",
  "maxFps": 10
}
```

`maxFps` caps how many frames per second the server sends to this client (1 to 120). Set `0` to remove the cap (the default). Each client controls its own rate; other connected clients are unaffected.

### Ack pacing

Push pacing hands each frame to the socket as soon as the rate allows, so a client that stalls drains what the transport buffered. To get one frame at a time instead, opt into ack pacing:

```json
{
  "type": "config",
  "pacing": "ack"
}
```

The server then keeps at most one frame in flight and waits for the client to acknowledge it:

```json
{
  "type": "ack",
  "seq": 41
}
```

Every `frame` message carries a monotonic `seq`. Echo the id of the frame you finished rendering. While an ack is outstanding, newer frames replace each other in the server and never reach the socket, so a client that stalls for ten seconds and resumes receives the current page rather than ten seconds of history. This mirrors how Chrome paces its own screencast upstream with `Page.screencastFrameAck`.

Under ack pacing one frame is in flight at a time, so the rate is one frame per transfer plus one acknowledgement round trip. Both the link's bandwidth and its latency bound it, and a link whose bandwidth-delay product exceeds a single frame goes underused. That headroom is the cost of the freshness guarantee.

Ack pacing bounds one hop. With a proxy in the path, forward the renderer's acks; acks generated on receipt leave frames queued on the far side.

Acks are cumulative: acknowledging a newer id covers every older one, so a client that skips ids still unblocks delivery. A client that opts in and then stops acknowledging simply stops receiving frames, while status, tabs, url, and console keep flowing. Send `{"type":"config","pacing":"push"}` to return to the default.

`pacing` and `maxFps` are independent and compose: pacing bounds how much is in flight, `maxFps` bounds the rate. A preview on a constrained link usually wants both.

A `config` message cannot cover the connection's opening frame, because the server sends the most recent frame as soon as the client connects. To have pacing apply from the very first frame, declare it on the URL instead:

```
ws://127.0.0.1:<port>/?pacing=ack&maxFps=10
```

A `config` message sent later still wins. An unrecognized or unparsable value on the URL is ignored rather than failing the connection.

## Input injection

Send input events to control the browser remotely. Mouse, keyboard, and touch input reset the daemon idle timer, so an actively controlled dashboard or streaming session is not shut down by the default timeout.

### Mouse events

```json
// Click
{
  "type": "input_mouse",
  "eventType": "mousePressed",
  "x": 100,
  "y": 200,
  "button": "left",
  "clickCount": 1
}

// Release
{
  "type": "input_mouse",
  "eventType": "mouseReleased",
  "x": 100,
  "y": 200,
  "button": "left"
}

// Move
{
  "type": "input_mouse",
  "eventType": "mouseMoved",
  "x": 150,
  "y": 250
}

// Scroll
{
  "type": "input_mouse",
  "eventType": "mouseWheel",
  "x": 100,
  "y": 200,
  "deltaX": 0,
  "deltaY": 100
}
```

### Keyboard events

```json
// Key down
{
  "type": "input_keyboard",
  "eventType": "keyDown",
  "key": "Enter",
  "code": "Enter"
}

// Key up
{
  "type": "input_keyboard",
  "eventType": "keyUp",
  "key": "Enter",
  "code": "Enter"
}

// Type character
{
  "type": "input_keyboard",
  "eventType": "char",
  "text": "a"
}

// With modifiers (1=Alt, 2=Ctrl, 4=Meta, 8=Shift)
{
  "type": "input_keyboard",
  "eventType": "keyDown",
  "key": "c",
  "code": "KeyC",
  "modifiers": 2
}
```

### Touch events

```json
// Touch start
{
  "type": "input_touch",
  "eventType": "touchStart",
  "touchPoints": [{ "x": 100, "y": 200 }]
}

// Touch move
{
  "type": "input_touch",
  "eventType": "touchMove",
  "touchPoints": [{ "x": 150, "y": 250 }]
}

// Touch end
{
  "type": "input_touch",
  "eventType": "touchEnd",
  "touchPoints": []
}

// Multi-touch (pinch zoom)
{
  "type": "input_touch",
  "eventType": "touchStart",
  "touchPoints": [
    { "x": 100, "y": 200, "id": 0 },
    { "x": 200, "y": 200, "id": 1 }
  ]
}
```

## Programmatic API

For advanced use, control streaming directly via the TypeScript API:

```typescript
import { BrowserManager } from 'agent-browser';

const browser = new BrowserManager();
await browser.launch({ headless: true });
await browser.navigate('https://example.com');

// Start screencast with callback
await browser.startScreencast((frame) => {
  console.log('Frame:', frame.metadata.deviceWidth, 'x', frame.metadata.deviceHeight);
  // frame.data is base64-encoded image
}, {
  format: 'jpeg',  // or 'png'
  quality: 80,     // 0-100, jpeg only
  maxWidth: 1280,
  maxHeight: 720,
  everyNthFrame: 1
});

// Inject mouse event
await browser.injectMouseEvent({
  type: 'mousePressed',
  x: 100,
  y: 200,
  button: 'left',
  clickCount: 1
});

// Inject keyboard event
await browser.injectKeyboardEvent({
  type: 'keyDown',
  key: 'Enter',
  code: 'Enter'
});

// Inject touch event
await browser.injectTouchEvent({
  type: 'touchStart',
  touchPoints: [{ x: 100, y: 200 }]
});

// Check if screencasting
console.log('Active:', browser.isScreencasting());

// Stop screencast
await browser.stopScreencast();
```

## Use cases

- **Pair browsing** - Human watches and assists AI agent in real-time
- **Remote preview** - View browser output in a separate UI
- **Recording** - Capture frames for video generation
- **Mobile testing** - Inject touch events for mobile emulation
- **Accessibility testing** - Manual interaction during automated tests
