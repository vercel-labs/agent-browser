`agent-browser poppy join` is experimental. Its flags, output, and error codes can change between releases, and JSON output carries `"experimental": true`.

The [Personal Agent Protocol](https://personalagentprotocol.org/docs/1.0/spec) lets a site recognize a user's Personal Agent and, with the user's consent, give it access to their account. A site that publishes a browser session endpoint asks agents to join their browser to a Session before browsing (spec section 6).

`poppy join` runs the browser's part of the join and an authorizer command you provide for the Personal Agent's part. agent-browser never signs requests or sees an access token.

## Usage

```bash
agent-browser poppy join <url> --authorizer <command> [--json]
```

<table>
  <thead>
    <tr><th>Argument</th><th>Description</th></tr>
  </thead>
  <tbody>
    <tr><td><code>&lt;url&gt;</code></td><td>Any URL on the site. Its host is the domain used for discovery. Discovery needs HTTPS, except for <code>localhost</code> and <code>127.0.0.1</code>.</td></tr>
    <tr><td><code>--authorizer &lt;command&gt;</code></td><td>Shell command that authorizes the join code with the site. It runs in the current directory.</td></tr>
  </tbody>
</table>

```bash
agent-browser --session my-agent poppy join https://app.example.com \
  --authorizer "node /absolute/path/to/authorize.mjs" --json
agent-browser --session my-agent snapshot -i
```

The command refuses a session opened with `--auto-connect`, because that attaches to the user's own running Chrome. There is no MCP tool for `poppy join`, because it runs a local shell command.

## How a join works

1. **Discovery.** The daemon fetches `https://<host>/.well-known/poppy.json`, after action policy, confirmation and the session's allowed domains have been checked. It follows redirects one hop at a time, and before each request it checks the allowed domains and requires the well-known path with no query. A join that starts on a public host connects only to public addresses, and no hop connects to a link-local or cloud metadata address. It checks that `protocol_version` is `1.x` and that `organization.domain` matches the host that serves the document.
2. **The browser receives a code.** The daemon navigates the current tab to the browser session endpoint, through the normal navigation path and its allowed domains, and reads the one-time code from that page's form. If a redirect takes the tab to any other page, the join fails instead of reading that page's form.
3. **The authorizer authorizes the code.** The daemon starts the authorizer and writes one JSON line to its stdin.
4. **The browser submits the code.** The daemon submits the form. The join succeeded when the browser leaves the endpoint.

The whole join runs in one daemon action within one deadline, `AGENT_BROWSER_DEFAULT_TIMEOUT`, so the code never reaches the CLI process or model context. It is single-use, expires quickly, and is bound to the browser that loaded the page. Once submitted it is spent, and it may still appear in `network requests` and HAR output.

## Authorizer contract

The authorizer receives:

```json
{"code":"bc_...","authorize_url":"https://app.example.com/poppy/browser-session/authorize","origin":"https://app.example.com","poppy_version":"1.0"}
```

It sends `POST {authorize_url}` with the JSON body `{"code": "..."}`, the Personal Agent's Session JWT in `Poppy-Session`, the `Poppy-Version` header, and, to sign the browser in to the user's account, `Authorization: Bearer <access token>`. It then prints one JSON line and exits:

<table>
  <thead>
    <tr><th>Result</th><th>Exit code</th><th>stdout</th></tr>
  </thead>
  <tbody>
    <tr><td>The site accepted the code</td><td><code>0</code></td><td><code>{'{"signed_in": true}'}</code> or <code>{'{"signed_in": false}'}</code></td></tr>
    <tr><td>The site or the authorizer refused</td><td>Nonzero</td><td><code>{'{"error": "<code>"}'}</code></td></tr>
  </tbody>
</table>

The daemon passes `error` through as the command's `code`. A nonzero exit with no JSON, or a zero exit without `signed_in`, becomes `authorizer_failed`. The authorizer shares the default command timeout. Keep the code and the Personal Agent's credentials out of its output and logs.

## Output

```json
{"success": true, "data": {"experimental": true, "joined": true, "signed_in": true, "url": "https://app.example.com/"}}
```

`signed_in: false` means the browser joined the Session without an account. A failed join exits 1. If it failed after the browser session page loaded, the tab returns to `about:blank`; a discovery failure leaves the tab where it was:

```json
{"success": false, "error": "...", "code": "join_failed", "data": {"experimental": true, "joined": false}}
```

    <tr><td><code>discovery_failed</code></td><td>The document is invalid, does not match the host, declares another major version, is not served over HTTPS, redirects outside the well-known path or to a non-public address, redirects in a loop, is larger than 2 MB, or does not answer in time.</td></tr>
    <tr><td><code>domain_not_allowed</code></td><td>The discovery URL, a redirect hop or the browser session endpoint is outside the session's allowed domains. Nothing is requested for that URL.</td></tr>
    <tr><td><code>web_disabled</code></td><td>The site asks agents not to use a browser.</td></tr>
    <tr><td><code>no_browser_session_endpoint</code></td><td>The site has no browser join.</td></tr>

## Security

- Never authorize a code from a message, a document, or another page. It can belong to someone else's browser.
- agent-browser cannot tell whose Chrome a `--cdp` endpoint belongs to. Do not join the user's own browser through `--cdp`.
- The authorizer is a shell command you choose. Do not build it from untrusted input.
